Macros — help

1. Один «барабан» и много «иголочек»

В модуле один Lua-интерпретатор на всё устройство. При старте файл прочитывается один раз: из него извлекаются правила, регистрируются в общем списке, после чего файл закрывается. При срабатывании правило либо выполняет декларативный bus-вызов (set/call/calls), либо перечитывает файл и вызывает нужный named-handler (run). Поэтому десятки макросов не съедают heap на отдельные интерпретаторы.

2. Формат файла

Файл возвращает таблицу с полем rules (массив). Каждое правило — составное условие when плюс ровно одно действие.

return {
    desc = "краткое описание для таблицы",
    handlers = {                       -- необязательно; только для run="..."
        apply = function(ev) set("e7.effect", ev.args[1]) end,
    },
    rules = {
        { when = { cron = "0 * * * * *", cond = { res = "wifi.connected", op = "==", val = true } },
          call = "e7.speed", args = { 50 } },
        { when = { term = "temp 25" },   set = "e7.effect", value = 1 },
        { when = { button = "start" },   call = "e7.speed", args = { 50 } },
        { calls = {                     -- правило без when: тело по открытию мета-окна
            { name = "e7.effect", args = { 2 } },
            { name = "e7.speed",  args = { 30 } },
        } },
    },
}

3. Составной триггер `when`

Все поля when объединяются по AND: правило срабатывает, когда истинны все условия одновременно.

Допустимые «первичные» триггеры внутри when (максимум один на правило):

  • cron — «наступил момент времени, совпадающий с выражением» (проверяется на тике);
  • term — пришёл term-токен с этим спецификатором (macro msg);
  • button — пришла button-команда (macro btn / кнопка веб-страницы);
  • on — пришло событие ресурсной шины с этим именем (подписку оформляет движок).

cond — не триггер, а проверка; их может быть до 4 (одна таблица или массив), все складываются в AND вместе с первичным триггером и/или самостоятельно.

Если первичных триггеров больше одного — ошибка разбора when: at most one of cron/term/button/on. Триггер-поля на верхнем уровне правила (вне when) — ошибка triggers must be inside when = {...}.

Три сценария правила:

whenСрабатывает
один триггер + 0..4 condпо триггеру И при всех истинных cond
только cond (без триггера)по фронту false -> true (один раз на переход)
нет when (или пустой)body: один раз при открытии мета-окна; без меты — один раз при старте

4. Действия правила

У правила должно быть ровно одно действие:

  • set = "ns.field" + value = N — запись в ресурс состояния (для ресурса с write-функцией — вызов функции, см. §7);
  • call = "ns.func" + args = { ... } — один bus-вызов;
  • calls = { {name=, args=}, ... } — несколько bus-вызовов (до 4);
  • run = "имя" + args = { ... } — named-handler из handlers (тяжёлый путь, см. §5).

Больше одного действия — ошибка rule has multiple actions. Если функция шины асинхронная, движок вызывает её сам (результат пишется в лог); из Lua асинхронные вызовы недоступны.

5. Когда использовать `run`

run перечитывает и компилирует файл при каждом срабатывании — это тяжёлый путь. Используйте его только для редкой логики (реже раза в минуту), когда действительно нужны ветвления, циклы или замыкания. Для массовых макросов — set/call/calls.

6. Условия cond

Условие — таблица {res, op, val}, их можно объединить в массив (AND). Поддерживаются операторы:

  • ==, != — равенство/неравенство;
  • <, <=, >, >= — числовое сравнение;
  • changed — сработать при любом изменении значения (см. §8).
{ when = { cond = { res = "wifi.rssi", op = "<", val = -70 } }, set = "e7.brightness", value = 10 }
{ when = { cron = "0 * * * * *", cond = {
      {res="wifi.connected", op="==", val=true},
      {res="time.valid",     op="==", val=true} } }, run = "onOk" }

7. `set` на ресурсах с write-функцией

Если у ресурса зарегистрирована write-функция (dual state+func, как e7.effect), set = "ns.field", value = N вызывает функцию с указанным значением — эффект применяется к железу, а значение ресурса обновляется внутри модуля. Для чистых state-ресурсов (без функции) set обновляет значение в реестре — модуль сам прочитает его в своём loop().

Проверить наличие write-функции — двойной клик в дереве ресурсов (func: true в свойствах) или info("ns.field") в Lua.

Требует уточнения в будущем: если появится модуль, реагирующий на state только через внешнюю write-функцию без чтения в loop(), семантика set может быть пересмотрена (предпочтение call).

8. `cond` с `op = "changed"` в правилах `on`/`term`/`button`

Для правила с первичным триггером (on/term/button) changed сравнивает значение с моментом предыдущего срабатывания этого же правила, а не с предыдущим тиком. То есть для when = { on = "X", cond = { res = "Y", op = "changed" } }: сработать на событие X, если Y изменилось с прошлого X.

Для правил без первичного триггера (when = { cond = changed }) changed сравнивается с предыдущим тиком.

9. Мета-cron — гейт окна

Поле meta_cron в возвращаемой таблице задаёт окно, в котором сценарий активен: meta_cron = "*/10 * * * * *" — каждые 10 секунд. Если поля нет — сценарий активен всегда. Мета-cron сам тело не запускает, он лишь «открывает окно» для правил файла. Невалидный meta_cron → err = "cron error", сценарий не запускается.

Если в файле единственное cron-выражение, его выносят в meta_cron (поле файла), а правило оставляют телом ({ set = ... } или { call = ... }). Для «диапазона» в мете секунды и минуты должны быть *.

Мета-cron — часть файла .lua и сохраняется вместе с ним. Колонка cron в таблице показывает значение из активного сценария (read-only); после остановки файла колонка пуста, потому что скрипт не распарсен.

10. Lua внутри named-handler

Доступны: get, set, call, has, info, mode, puts/print, clock, now. Нет on/off/call_async — события оформляются правилом on, асинхронность — на стороне движка. Всё это доступно только внутри run=-пути.

Handler получает один аргумент — таблицу события:

  • ev.type — "cron"|"cond"|"term"|"button"|"on"|"body";
  • ev.spec — cron/term/button/имя события;
  • ev.args — массив аргументов из правила;
  • ev.value — значение ресурса (для cond, если есть).

Каждый вызов handler получает свежее окружение: глобальные переменные между вызовами не сохраняются. Если нужно помнить значение — храните его в ресурсе core_state.

11. Ошибки

  • triggers must be inside when = {...} — триггер-поле задано вне when.
  • when: at most one of cron/term/button/on — в when больше одного первичного триггера.
  • rule has multiple actions — задано больше одного действия.
  • rule has no action (set/call/calls/run) — действие не задано.
  • set: use call= for function resource <name> — ресурс — чистая функция.
  • set: value required — у set нет значения.
  • cron error: ... — невалидный cron в правиле или в мете.
  • File is empty or unreadable — файл пуст/недоступен.
  • No memory for interpreter / No memory for rules — не хватило heap; авто-повтор ограничен, затем нажмите Reload.
  • call: not found <name> / call <name> <текст ошибки> — ресурс не найден/ошибка вызова.
  • handler not found: <name> — в handlers нет такого имени.
  • ERR: stop scenario first — попытка сохранить запущенный сценарий.

12. Лимиты

  • Файлов в списке — до 30.
  • Правил в файле — до 8; cond в правиле — до MACRO_MAX_CONDS = 4; bus-вызовов в правиле — до 4; аргументов в вызове — до 4.
  • Инструкций Lua на один вызов handler — MACRO_LUA_MAX_OPS = 100000.
  • Бюджет heap модуля — 100 КБ; при превышении ~95% кнопка «Валидация макросов» показывает критическое состояние.

13. Синтаксис cron

6 полей (секунды минуты часы день месяца месяц день недели), необязательное 7-е — год. Допустимы *, */N, a-b, a-b/N, a,b,c, ?. Генератор — на странице CRON helper.
