# Модуль macros — сценарии на Lua + встроенный cron

Модуль `module_macros` превращает прошивку AVR-FOTA (ESP32) в устройство с **пользовательскими
сценариями**: файлы-сценарии на языке **Lua 5.4** с планировщиком по типу Cron. Сценарий может
«срабатывать по моменту времени» (cron), «по условию» (фронт ложь→истина) и «по событию»
(слово из терминала / кнопка). Модуль — прототип и каркас для дальнейшего расширения:
в будущем другие модули прошивки смогут регистрировать для сценариев свои данные и методы.

Содержимое:
- веб-страница-менеджер файлов сценариев (`/macros.html`);
- набор Lua-сценариев в папке файловой системы `/macros/*.lua`;
- интерпретатор **Lua 5.4.7** (движок **EspLuaEngine**, вендорен в `EspLuaEngine/`);
- планировщик cron на базе **ccronexpr** (supertinycron) + time-мост на `common/TimeLib`;
- метафайл `/config_macros.json` (список, приоритеты, состояния, даты создания);
- отладка и управление через терминал (команды `macro ...`).

Модуль предназначен **только для ESP32** (поддержка ESP8266 удалена).

---

## 1. Что это и зачем

Прошивка получает гибкую «логику пользователя», которую не нужно перекомпилировать:

```
Пользователь пишет файл-сценарий на Lua:
    cron("*/10 * * * * *", function()
        puts("tick every 10s")
    end)

    term("temp 25", function()
        report("sensor: temp 25")
    end)

Модуль при запуске сценария исполняет файл в состоянии Lua и строит
«таблицу условий и моментов времени», а тик раз в секунду проверяет:
  — совпал момент времени?    → выполнить тело cron-правила;
  — условие стало истинным?    → выполнить тело cond-правила (по фронту);
  — пришло событие из терминала/веба → выполнить тело term/button-правила.
```

Все правила одного файла живут в **одном интерпретаторе**: переменные (в т.ч. замыкания) и
функции сохраняются между срабатываниями.

## 2. Как подключить и собрать

Окружение-прототип описано в `src/module_macros/module_macros.ini`:

```ini
[env:esp32_macrotest]
extends = env:esp32
src_filter = ${platformio.src_filter} +<module_macros/> +<module_udp/> +<module_otaclient/>
build_flags=
    -D CONNECTION_LED=2
    -D AP_ENABLE_BUTTON=-1
    -D USE_LITTLEFS
    -D MODULE_UDP=1
    -D MODULE_MACROS=1
    -D DEBUG_MACROS=1
    -D MODULE_OTACLIENT=1
    -D DEBUGLOG_WIFI
    -D RELEASE
```

Сборка (файл `src/modules_registry.cpp` автогенерируется под выбранный env):

```bash
python python/module_registry_gen.py --env esp32_macrotest
pio run -e esp32_macrotest
```

Флаги макрос-окружения:
- `DEBUG_MACROS` — журнал модуля (не гейтится `RELEASE`);
- `RELEASE` — гасит общие логи (`DEBUGLOG` core_web/json), остаются только macros и wifi;
- `DEBUGLOG_WIFI` — логи Wi-Fi.

**Важно:** env `esp32_macrotest` использует собственную таблицу партиций
`partitions_esp32_macro.csv` (лежит в корне ядра): app0/app1 по 1344 КБ (Lua-движок),
spiffs 1336 КБ. Остальные env используют `partitions_esp32.csv`. При прошивке макротеста
на устройство, собранное с другой таблицей разделов, нужно перепрошить таблицу разделов
(обычно делается автоматически при `pio run -t upload`).

После прошивки:
1. Модуль создаёт каталог `/macros/` (если его нет). Файлы-примеры приходят с файловой
   системой (см. `src/module_macros/web/macros/*.lua`), `4_fs_builder.py` раскладывает их
   в образ FS с сохранением подкаталога.
2. При первом проходе список файлов синхронизируется с метафайлом `/config_macros.json`
   (новые `.lua` добавляются с приоритетом 7 и в состоянии «стоп», записи об отсутствующих
   файлах удаляются).
3. Откройте `/macros.html` или воспользуйтесь терминалом.

## 3. Веб-страница `/macros.html`

Страница-менеджер файлов сценариев.

### Таблица-список
Колонки (порядок можно менять, перетаскивая заголовки; порядок сохраняется в
`localStorage` браузера):
- чекбокс выбора;
- **приоритет** (0 — высший, 7 — низший);
- имя файла;
- размер;
- состояние: «запущен» / «стоп» / «ошибка» (текст ошибки — в всплывающей подсказке);
- дата создания.

Клик по строке выделяет её (подсветка). Двойной клик по строке открывает файл в
редакторе (`edit.html`, новая вкладка).

### Кнопки панели (сверху)
- **Обновить список** — перечитать `/macros/list` вручную (авто-опроса нет, чтобы не
  грузить устройство);
- **Создать** — создать новый файл (`new_macros.lua`, при занятости имени — с номером);
- **Запустить** / **Остановить** — по выбранным (работают и для группы);
- **Перечитать** — перечитать выбранный сценарий (или все) — пересборка происходит в
  фоне (в течение ~1 с тиком);
- **Редактировать** — открыть выбранный файл в `edit.html`;
- **Переименовать** — имя файла в строке становится полем ввода;
- **Приоритет − / +** — изменить приоритет выбранного файла;
- **Удалить** — удалить выбранные (всегда с подтверждением).

Правила активности: «Запустить/Остановить/Удалить» активны при ≥1 выбранном,
«Редактировать/Переименовать/Приоритет±» — при ровно одном. Активные кнопки — зелёные,
неактивные — серые. Во время любого запроса рядом с кнопками мигает «…».

### Веб-API (все — GET, состояние в query)
| URL | Назначение |
|-----|-----------|
| `/macros/list` | JSON-список файлов |
| `/macros/create?name=` | создать файл сценария |
| `/macros/delete?name=` | удалить (имена через запятую) |
| `/macros/rename?old=&new=` | переименовать |
| `/macros/state?name=&on=1|0` | запустить/остановить |
| `/macros/prio?name=&dir=+1|-1` | изменить приоритет |
| `/macros/reload?name=` | перечитать (без name — все) |
| `/macros/fire?type=&token=` | внешнее событие (резерв) |
| `/macros/resources` | каталог ресурсов шины (JSON) |
| `/macros/validate?cron=&body=` | валидация cron и синтаксиса Lua |
| `/macros/cron?name=&cron=` | мета-cron файла (гейт окна) |
| `/macros/get?name=` | чтение содержимого сценария |
| `/macros/save?name=&body=` | запись содержимого сценария |
| `/macros/ver` | версия модуля |

Файлы `.lua` открываются в `module_editor` (`edit.html`) как текстовые (расширение `lua`
добавлено в распознавание текста редактора).

## 4. Терминал

Команды регистрируются модулем лениво при первом вызове `TerminalLoop()`. Общий вид:

```
macro list                         — список сценариев и число правил
macro run <file.lua>               — запустить сценарий
macro stop <file.lua>              — остановить
macro reload [file.lua]            — перечитать (без имени — все)
macro prio <file.lua> <+1|-1>      — изменить приоритет
macro msg <слова...>               — событие для term-правил (полное совпадение всех слов)
macro btn <имя...>                 — событие для button-правил
```

Пример:

```
macro run ex_input.lua
macro msg temp 25
   → [MACRO] event term "temp 25" queued
     [MACRO] condition term "temp 25" fired
     [MACRO] 18:05:38
     [MACRO] sensor: temperature 25
macro btn start
   → [MACRO] condition button "start" fired
     [MACRO] button start pressed
```

Примечания: вывод в терминале — только латиница; сообщения модуля начинаются с
`[MACRO]`; тело правила печатается функциями `puts`/`print` (с префиксом `[MACRO]`).

## 5. Язык сценариев (Lua)

Файл сценария — это Lua-скрипт, который возвращает **таблицу** `{handlers, rules}`. Модуль
читает файл один раз при старте, разбирает `rules` в общий список и закрывает файл. При
срабатывании правило делает декларативные bus-вызовы или перечитывает файл и вызывает
named-handler в свежем окружении (глобалы между вызовами не сохраняются).

### Формат сценария

Файл **обязан** вернуть таблицу с полем `rules` (массив).

```lua
return {
    desc = "Описание для web-таблицы",
    handlers = {                      -- необязательно; для run="..."
        apply = function(ev) set("e7.effect", ev.args[1]) end,
    },
    rules = {
        { cron = "*/10 * * * * *", call = "e7.speed", args = { 20 } },
        { cron = "0 30 * * * *",   calls = { {"e7.effect", {2}}, {"e7.color", {255}} } },
        { cond = { res = "wifi.connected", op = "==", val = true }, run = "apply", args = { 1 } },
        { term = "temp 25", run = "apply", args = { 25 } },
        { button = "start", run = "apply" },
        { on = "wifi.just_connected", run = "apply" },
        { run = "apply" },            -- тело: по открытию мета-окна
    },
}
```

- `cond` — декларативное условие (`res`+`op`+`val`, массив = AND), фронт ложь→истина.
- `term`/`button` — полное совпадение спецификатора (терминал `macro msg`/`macro btn`).
- `on` — событие ресурсной шины (подписку оформляет движок).
- У правила ровно одно действие: `call`+`args`, `calls` или `run`+`args`.

### API ресурсной шины (внутри named-handler)
- `get("ns.field")` — чтение ресурса;
- `set("ns.field", value)` — запись (для функций — вызов с одним аргументом), возвращает код;
- `call("ns.func" [, args...])` — вызов; значение или `(nil, rc)`;
- `has("ns.field")`, `info("ns.field")` (таблица метаданных), `mode("namespace" [, value])`;
- `puts(...)` / `print(...)` — вывод в терминал с префиксом `[MACRO]`;
- `now()` — текущие секунды; `clock()` — время «ЧЧ:ММ:СС»;
- **нет** `on`/`off`/`call_async` — события оформляются правилом `on`, асинхронные функции
  движок вызывает сам;
- окружение свежее на каждый вызов: глобалы между срабатываниями не живут (храните состояние
  в ресурсах `core_state`).

### Двухуровневый cron
1. **Мета** (колонка `cron` в web-таблице) — гейт окна. Если заполнен, сценарий работает
   только в секунды, совпадающие с выражением; невалидный cron → `err = "cron error"`.
2. **Правила** (`rules[].cron`) работают внутри разрешённого окна.

5 полей автоматически дополняются ведущим `0` (секунды). Cron требует NTP.

### Простой пример

```lua
-- Мета-cron задан в web-таблице (например, */10 * * * * *), правило — тело.
return {
    desc = "tick every 10s",
    handlers = {
        tick = function(ev) puts(clock(), "fired:", ev.type, ev.spec) end,
    },
    rules = {
        { run = "tick" },
    },
}
```

Действие можно выразить декларативно (`call`/`calls`) — тогда Lua в момент срабатывания
не используется. Handler вызывается со свежим окружением; при превышении лимита инструкций
VM (защита от бесконечных циклов) исполнение прерывается ошибкой.

## 6. Справка по CRON

Выражение — **6 полей** (интерпретатор всегда ожидает секунды первым):

```
секунды   минуты   часы   день-месяца   месяц   день-недели
```

- секунды 0–59, минуты 0–59, часы 0–23;
- день месяца 1–31, месяц 1–12 (или `JAN`–`DEC`), день недели 0–7 (0 и 7 = воскресенье,
  или `SUN`–`SAT`);
- возможны 5 полей (без секунд — станут 0) и 7 полей (год опционально).

Синтаксис поля: `*` — любое; `*/N` — каждые N; `a-b` — диапазон; `a-b/N` — шаг в
диапазоне; `a,b,c` — список; `?` — как `*`.

### Примеры

```lua
cron("*/10 * * * * *", function() ... end)  -- каждые 10 секунд
cron("0 * * * * *",    function() ... end)  -- каждая минута (в 0-ю секунду)
cron("15 42 * * * *",  function() ... end)  -- каждый час в 00:42:15
cron("0 0 * * * *",    function() ... end)  -- каждый час в 00:00:00
cron("0 0 */2 * * *",  function() ... end)  -- каждые 2 часа
cron("0 30 */4 * * *", function() ... end)  -- каждые 4 часа в :30 (00:30, 04:30, ...)
cron("0 0 9 * * 1",    function() ... end)  -- по понедельникам в 09:00
cron("0 0 9 * * 1,2,4",function() ... end)  -- пн+вт+чт в 09:00
cron("0 0 9 * * 1-5",  function() ... end)  -- будни в 09:00
cron("0 0 9 2-30/2 * *", function() ... end)-- чётные числа месяца в 09:00
cron("0 0 9 5 * *",    function() ... end)  -- 5-го числа каждого месяца в 09:00
cron("0 0 9 */5 * *",  function() ... end)  -- 1,6,11,... числа месяца в 09:00
cron("0 0 9-17 * * *", function() ... end)  -- каждый час с 09:00 до 17:00 включительно
cron("0 0 9-17 * * 1-5", function() ... end)-- будни с 09:00 до 17:00
```

Cron срабатывает **только после синхронизации NTP**; расписание считается в локальном
времени. Планировщик хранит у каждого cron-правила «следующий момент» (`cron_next` из
ccronexpr), при совпадении `now() >= next` выполняет тело и сразу считает следующий
момент — пропущенное не «догоняется».

## 8. Как это устроено внутри

### Поток данных

```
web (/macros.html) ──GET──▶ web_Init-эндпоинты  → только FS + /config_macros.json + флаг
                                      │
                              SetTimerTask(tick, 1000)   (main loop)
                                      │
              изменение списка (gen) → пересборка набора запущенных сценариев
                                      │
        для каждого запущенного файла (свой EspLuaEngine/lua_State и таблица сущностей):
          cron:  now() >= next        → тело; next = cron_next(expr, now())
          cond:  вычислить условие (функцию), фронт false→true → тело
          term/button: события из очереди (терминал/HTTP) → тело
```

- Интерпретатор Lua и планировщик вызываются **только в main-loop контексте** (тик EERTOS
  и терминал); веб-обработчики не трогают интерпретатор — они меняют мету/FS и помечают
  файл на перерегистрацию, а тик разбирает правила.
- **Один** `EspLuaEngine` (`_lua`) на весь модуль. При старте `registerFile()` разбирает
  `rules` файла в `MacroFile.rules` и закрывает файл; отдельные `lua_State` на файл больше
  не создаются. При срабатывании правило делает декларативные bus-вызовы или перечитывает
  файл и вызывает named-handler (`run="..."`) в свежем `_ENV`.
- Lua-вызовы защищены счётчиком VM-инструкций (`MACRO_LUA_MAX_OPS`, count-hook) — при
  превышении исполнение прерывается ошибкой, устройство не виснет.

### Структуры данных (module_macros.h / module_macros_engine.h)

- `MacroFile` — файл-сценарий: метаданные (`name`, `prio` 0..7, `run`, `created`,
  `metaCron`, кэш `size`) + runtime (`active`, `err`, `desc`, `needParse`, `parseFails`,
  массив `rules` в heap, разобранный `metaExpr`).
- `MacroRule` — правило: `type` (cron/cond/term/button/on/body), `spec`, для cron —
  `cron_expr` + `next`, `condSpec` (сериализованная AND-цепочка `res|op|val`),
  действие — `handler`/`handlerArgs` (Lua) или `actions[]` (декларативные bus-вызовы).
- `MacroEvent` — элемент очереди внешних событий (term/button/on).
- `strMacrosConfig` — `enabled`.
- Ограничения (ESP32): до 30 файлов, до 8 правил в файле, до 4 bus-вызовов в правиле,
  до 4 аргументов в вызове. Бюджет heap модуля — 100 КБ (проверка `/macros/heap`).

### Метафайл `/config_macros.json`

```json
{
  "enabled": true,
  "files": [
    { "name": "/macros/ex_10s.lua", "prio": 7, "run": false, "created": 1788545122 }
  ]
}
```

Список для веба = сканирование `/macros/*.lua` + наложение меты (новые файлы
авто-добавляются, записи про отсутствующие удаляются). Размер файла берётся при
формировании списка.

## 9. Ограничения прототипа (важно)

- Модуль собирается и работает **только на ESP32**.
- Интерпретатор Lua использует heap; состояние создаётся только для **запущенных** файлов.
  Каждое состояние Lua заметно тяжелее старого pTcl, поэтому одновременно лучше держать
  запущенными несколько файлов (не все 16) и следить за свободной памятью.
- Тела и условия должны быть короткими: они исполняются в main-loop (тик раз в секунду).
  Бесконечные циклы прерываются по лимиту инструкций.
- Приоритет 0..7 пока информационный (сортировка/порядок исполнения в будущем).
- Перечитывание файлов — только вручную (старт/стоп/кнопка «Перечитать»/терминал);
  авто-детекта изменения файла по mtime нет.
- Cron требует синхронизации NTP (время локальное); `cond`/`term`/`button` работают без NTP.
- Старые пользовательские файлы `*.tcl` (от версии на pTcl) не запускаются и не видны в
  списке — сценарии нужно пересоздать на Lua. Автоматической конвертации нет.
- Перепрошивка FS-образа перезаписывает пользовательские правки (файлы сценариев и
  мета-конфиг восстанавливаются из сборки) — стандартное поведение проекта.
- В терминал выводится только латиница (в коде — русские комментарии, в веб — русский
  интерфейс).

## 10. Дальнейшее развитие (вне прототипа)

Прототип закладывает точки расширения для взаимодействия модулей прошивки со сценариями:
- единый Lua-интерпретатор создаётся в одном месте (`initLua`), а регистрация правил —
  в `registerFile`; сюда позже добавится применение списка «биндингов» (Lua-функций/констант),
  которые каждый модуль зарегистрирует в своём `begin()` по образцу слотов
  `begin(ctx)`/`web_Init()`/`loop()`;
- регистрация функций уже использует механизм `EspLuaEngine::registerFunction(name, fn, userData)`
  — тем же путём модули смогут предоставлять сценариям и «данные для считывания»
  (функции-геттеры), и «методы взаимодействия» (обёртки над своим публичным API).
